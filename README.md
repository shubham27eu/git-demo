# Data Anonymization Toolkit

This project is a **Data Anonymization Toolkit** designed to protect sensitive information in datasets. It provides tools and processes to anonymize data effectively, making it suitable for analysis and sharing while preserving privacy.

It generates two primary executable JARs:
- `data-processor-main.jar`: The main application. It uses compile-time embedded paths for the primary data and attributes files. It also bundles and executes Python scripts at runtime to generate intermediate data files (`Sensitivity_Results.xlsx`, `KYU Score.xlsx`) which are then consumed. Runtime arguments are needed for the user ID (for KYU score lookup) and the specific SQL query to execute.
- `data-processor-mock-runner.jar`: A test runner that takes all its required file paths as command-line arguments.

## Functional Overview

This Data Anonymization Toolkit is designed to safeguard sensitive information within datasets, enabling data to be used for analysis or sharing while minimizing privacy risks. It achieves this through a configurable, multi-stage process:

1.  **Pre-processing (Python)**: Python scripts are executed first to analyze data characteristics and generate crucial metadata. This includes:
    *   `Sensitivity_Results.xlsx`: Defines the sensitivity level of various data attributes.
    *   `KYU Score.xlsx`: Provides "Know Your User" scores, which can influence the strictness of anonymization.
    These scripts and their outputs make the anonymization process adaptable to different data and risk contexts.

2.  **Core Anonymization (Java)**: The main Java application takes over, using the metadata generated by the Python scripts, along with a main dataset and an attributes configuration file (both specified at build time).
    *   It loads the data into an in-memory SQLite database.
    *   Based on the user's identity (KYU score), the sensitivity of data columns involved in their query, and predefined attribute characteristics, appropriate anonymization techniques (e.g., generalization, suppression, masking) are applied to the data relevant to the user's request.
    *   Finally, the user's SQL query is executed against this temporarily anonymized subset of data, returning only the necessary, privacy-protected information.

This approach allows for dynamic and context-aware data anonymization, tailored to specific user queries and risk profiles.

## Prerequisites

- **Java Development Kit (JDK)**: Version 17 or higher.
- **Maven**: For building the project (version 3.x).
- **Python 3**: Must be installed and accessible. The Java application will attempt to run Python scripts using `python3` (by default) or a Python interpreter found in a local `.venv` virtual environment.

### Python Environment Setup (Recommended)

It is **strongly recommended** to use a Python virtual environment to manage dependencies for this project and avoid conflicts with system-wide packages.

1.  **Create a virtual environment**:
    Navigate to your project's root directory (where you will run the Java JAR from) and run:
    ```bash
    python3 -m venv .venv
    ```

2.  **Activate the virtual environment**:
    -   On macOS and Linux:
        ```bash
        source .venv/bin/activate
        ```
    -   On Windows (Git Bash or similar):
        ```bash
        source .venv/Scripts/activate
        ```
    -   On Windows (Command Prompt):
        ```bash
        .venv\Scripts\activate.bat
        ```
    -   On Windows (PowerShell):
        ```bash
        .venv\Scripts\Activate.ps1
        ```
    You should see the name of the virtual environment (e.g., `(.venv)`) in your shell prompt after activation.

3.  **Install required Python packages**:
    Once the virtual environment is activated, install the necessary libraries:
    ```bash
    pip install pandas openpyxl
    ```
    (These are for the dummy scripts provided. Your actual Python ML scripts might have other dependencies.)

4.  **Running the Java Application with Virtual Environment**:
    - If a virtual environment named `.venv` is present in the directory where `data-processor-main.jar` is run, and it contains a Python interpreter at `.venv/bin/python3` (for Linux/macOS) or `.venv/Scripts/python.exe` (for Windows), the Java application will automatically attempt to use that interpreter to run the bundled Python scripts.
    - Otherwise, it will fall back to using the system-wide `python3` command (or `python` if `Main.java`'s `ProcessBuilder` configuration is changed).
    - **Important**: Ensure you run the `java -jar ...` command from the same directory where the `.venv` folder is located (typically your project root).

## Building and Running the Anonymization Toolkit

### Building the JARs

The project is built using Apache Maven, configured through the `pom.xml` file located in the project's root directory. This file defines the project structure, dependencies, and build plugins.

Two primary executable JAR files are generated:

1.  **`data-processor-main.jar`**: This is the main application JAR.
    *   **Executable "Uber" JAR**: The `maven-shade-plugin` is used to package this JAR as an "uber" JAR. This means it includes all necessary runtime dependencies bundled within it, making it self-contained and easier to run.
    *   **Embedding Data File Paths**:
        *   During the build, Maven properties passed on the command line (e.g., `-Ddata.df.path=./path/to/data.csv`) are used to specify the locations of the main data CSV and attributes CSV files.
        *   These paths are written into a `config.properties` file (located within `src/main/resources` and thus bundled into the JAR).
        *   The Java application reads this `config.properties` file at runtime to determine the locations of these essential data files.
    *   **Bundling Python Scripts**: Python scripts located in `src/main/resources/scripts/` are also bundled into this JAR. These scripts are extracted and executed at runtime by the Java application to generate intermediate data files.

2.  **`data-processor-mock-runner.jar`**: This JAR is a test runner.
    *   It is also packaged by the `maven-shade-plugin`.
    *   Unlike the main JAR, it does not use embedded paths from `config.properties` for its core data files; instead, it requires all necessary file paths as command-line arguments at runtime.

**Build Command:**

To build both JAR files, navigate to the project's root directory (where `pom.xml` is located) and run the following Maven command. Replace placeholder paths with the actual paths to your main data and attributes files for the `data-processor-main.jar`:

```bash
mvn clean package -Ddata.df.path=./path/to/your/Data_2019-20.csv \
                  -Dattributes.path=./path/to/your/Attributes.csv
```

**Explanation of Build-Time Properties (for `data-processor-main.jar`):**
-   `-Ddata.df.path`: Specifies the path to the main data CSV file (e.g., `Data_2019-20.csv`). This path is stored in the bundled `config.properties`.
-   `-Dattributes.path`: Specifies the path to the attributes definition CSV file (e.g., `Attributes.csv`). This path is also stored in the bundled `config.properties`.

If these properties are not provided during the build for `data-processor-main.jar`, they will default to placeholder values (e.g., `"path-not-set"`) within the `config.properties` file, which will likely cause runtime errors when `data-processor-main.jar` is executed as it won't find the required data.

Upon successful execution, this command will compile the code, run tests, and package the application. The primary outputs will be:
-   `target/data-processor-main.jar`
-   `target/data-processor-mock-runner.jar` (if its build is enabled in `pom.xml`)

### Running `data-processor-main.jar`

This JAR orchestrates the data anonymization process. When executed, it follows these steps:

1.  **Input Arguments**: The application starts by taking two command-line arguments:
    *   `<user_id>`: The ID of the user for whom the data is being processed. This ID is crucial for looking up their "Know Your User" (KYU) score.
    *   `<sqlite_query>`: The full SQLite query string that the user wishes to execute on the data *after* anonymization. The table name within this query should correspond to the main data (typically `data_df`).

2.  **Python Script Execution (Pre-processing)**:
    *   The JAR first extracts and executes two bundled Python scripts: `generate_sensitivity.py` and `generate_kyu_scores.py`.
    *   It attempts to use a Python interpreter from a local `.venv` virtual environment if present in the JAR's execution directory. Otherwise, it falls back to the system's `python3` interpreter (see "Python Environment Setup").
    *   `generate_sensitivity.py`: This script analyzes the data (details of which data it accesses for this are TBD, but likely related to the main dataset's characteristics) to determine attribute sensitivity. It outputs its findings to a file named `Sensitivity_Results.xlsx` in the current working directory (where the JAR was launched).
    *   `generate_kyu_scores.py`: This script generates or retrieves KYU scores for users. It outputs these scores to a file named `KYU Score.xlsx` in the current working directory.

3.  **Loading Data and Configuration**: The Java application then loads various data and configuration files:
    *   **Main Data CSV**: Reads the primary dataset from the CSV file whose path was embedded in `config.properties` during the build (e.g., `Data_2019-20.csv`).
    *   **Attributes Configuration CSV**: Reads the attributes definition file (e.g., `Attributes.csv`), also using the path from the embedded `config.properties`. This file likely defines the types of attributes in the main data and their characteristics.
    *   **Sensitivity Results**: Loads the `Sensitivity_Results.xlsx` file generated by the Python script. This file contains information about how sensitive each attribute or column in the dataset is considered.
    *   **KYU Scores**: Loads the `KYU Score.xlsx` file generated by the Python script.

4.  **In-Memory Database Setup**:
    *   The main data loaded from the CSV is then populated into an in-memory SQLite database. This allows the application to efficiently query and manipulate the data during the anonymization process using the provided SQL query. The table in this in-memory database is typically named `data_df`.

5.  **Determining Sensitivity and KYU Score**:
    *   **Sensitivity Levels**: The application uses the information from `Sensitivity_Results.xlsx` to understand the sensitivity level of different data attributes (columns) it will be working with.
    *   **User KYU Score**: It looks up the KYU score for the `<user_id>` (provided as a command-line argument) from the loaded `KYU Score.xlsx` data. The KYU score acts as a risk indicator for the user.

6.  **Anonymization Strategy Selection and Application**:
    *   Based on the sensitivity levels of the attributes involved in the user's SQL query, the user's KYU score, and the definitions in `Attributes.csv`, the application dynamically selects and applies appropriate anonymization strategies (e.g., generalization, suppression, masking) to the data in the in-memory SQLite database.
    *   The goal is to transform the data in such a way that the user's query can be executed while mitigating the risk of re-identification, according to the determined sensitivity and KYU score.

7.  **Query Execution and Output**:
    *   Once the relevant parts of the data in the in-memory SQLite database have been anonymized, the `<sqlite_query>` (provided as a command-line argument) is executed against this anonymized data.
    *   The final output of the `data-processor-main.jar` is the result set of this SQL query. This result is typically printed to standard output.

**Prerequisites for Running**:
- Review the main "Prerequisites" section, especially the Python environment setup.
Ensure Python scripts can write `Sensitivity_Results.xlsx` and `KYU Score.xlsx` to the JAR's working directory.

**Usage:**
```bash
java -jar target/data-processor-main.jar <user_id> "<sqlite_query>"
```

**Arguments:**
- `<user_id>`: The ID of the user. This ID is used to look up their KYU score from the `KYU Score.xlsx` file generated by the Python script.
- `<sqlite_query>`: The full SQLite query string to execute on the data loaded from the CSV file (specified by `data.df.path` at build time). **Important**: Enclose the query in double quotes if it contains spaces or special shell characters. The table name within the query should typically be `data_df`.

**Example:**
```bash
java -jar target/data-processor-main.jar "2" "SELECT * FROM data_df WHERE "2" = 'Gadag'"
```
Ensure you replace `"2"` with your desired user ID. The example query selects all columns for the row where column named "2" has the value 'Gadag'.

For more complex queries, especially those involving SQL `IN` clauses or other special characters, you might need more careful shell quoting. Here's an example demonstrating how to pass a query with an `IN` clause and quoted string literals, ensuring the column names (like `"2"`) are also correctly quoted for SQL if they are numeric or contain special characters:

```bash
java -jar target/data-processor-main.jar "2" 'SELECT "2", "18", "198" FROM data_df WHERE "2" IN ('"'"'Ramanagara'"'"', '"'"'Kolara'"'"')'
```
This example uses outer single quotes for the shell to treat the entire SQL query as one argument, and a common technique `'"'"'` to embed single quotes within the single-quoted string for the SQL string literals 'Ramanagara' and 'Kolara'. Alternatively, you can use outer double quotes and escape all inner double quotes and special characters as needed by your shell.

### Running `data-processor-mock-runner.jar`

The `data-processor-mock-runner.jar` serves as a testing tool, designed to run a predefined mock data scenario. Unlike `data-processor-main.jar`, it does not use embedded configuration or execute Python scripts; instead, it requires all necessary input file paths (main data, sensitivity results, and KYU scores) to be provided directly as command-line arguments.
(Note: The build configuration for this JAR might be commented out in the current `pom.xml`. If needed, ensure its execution block in the `maven-shade-plugin` is active and correctly configured).

**Usage:**
```bash
java -jar target/data-processor-mock-runner.jar <data_df_path> <sensitivity_results_path> <kyu_score_path>
```
**Arguments:**
- `<data_df_path>`: Path to the main data CSV file.
- `<sensitivity_results_path>`: Path to the sensitivity results Excel file.
- `<kyu_score_path>`: Path to the KYU score Excel file.

**Example:**
```bash
java -jar target/data-processor-mock-runner.jar path/to/Data_2019-20.csv path/to/Sensitivity_Results.xlsx path/to/KYU_Score.xlsx
```

## Using as a Library / Dependency

The `data-processor-main.jar`, once built with its embedded paths for `data.df.path` and `attributes.path`, can potentially be included as a dependency in other Maven projects.

If the JAR is available locally, you might consider installing it to your local Maven repository (`mvn install`) or using a system-scoped dependency.

**Example of System-Scoped Dependency (for local JAR):**
```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>data-processor-main</artifactId> <!-- This is the finalName from shade plugin -->
    <version>1.0-SNAPSHOT</version> <!-- Or the version built -->
    <scope>system</scope>
    <systemPath>${project.basedir}/path/to/data-processor-main.jar</systemPath>
</dependency>
```
**Note:** Using system scope has limitations and is generally not recommended. Installing the JAR to a local or remote Maven repository is a more robust approach.

When used as a library:
- The paths for `Data_2019-20.csv` and `Attributes.csv` would be used as configured during its build (embedded in `config.properties`).
- If you call `com.example.anonymization.Main.main()`, it will attempt to execute the bundled Python scripts. This means the consuming application's environment must also meet the Python 3 and library prerequisites (including having a `.venv` or system `python3` available, and necessary packages like `pandas` and `openpyxl` installed for that Python interpreter). The Python scripts must be able to write to the current working directory.

This would allow other applications to leverage the anonymization capabilities more directly.
